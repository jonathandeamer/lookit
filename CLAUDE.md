# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

`lookit` is a finger client (RFC 1288, TCP/79) for the modern terminal: an interactive Bubble Tea TUI, built with Charm tools.

**This file is the always-loaded layer, so it stays small.** Detail that only one
kind of session needs lives next to the work and is read on demand:
`finger/CLAUDE.md` and `tui/CLAUDE.md` (loaded when you touch those packages),
`docs/releasing.md` (cutting a release), `docs/tui-review/README.md` (looking at
the TUI). Keep new detail in those files; add to this one only what a session
must know before it knows what it's working on.

## Commands

```bash
make build                                   # build the binary (-> ./lookit)
make check                                   # the full CI gate set (run before committing)
make test                                    # tests without -race
make fmt                                     # gofmt -w . (fix formatting)
make vuln                                    # govulncheck dependency scan
make notices                                 # regenerate THIRD_PARTY_NOTICES.md after dep changes
make review-tui                              # record the TUI visual-review stills into out/tui-review/ (~7 min, not part of check)
make review-sheet                            # rebuild the per-tape contact sheets from frames already on disk
go test ./tui/ -run TestEnterInListDrills -count=1 -v   # single test
```

The `Makefile` is the single source of truth for the gate set, and CI calls `make check`, so a green `make check` locally is exactly what CI runs. `make check` runs four gates: `go vet ./...`, a `gofmt -l .` emptiness check, `golangci-lint run ./...`, and `go test ./... -race`. The `golangci-lint` gate uses the default linter set with the `std-error-handling` exclusion preset (see `.golangci.yml`), so unchecked `fmt.Fprint*`/deferred `Close` don't fail it; the linter version is pinned once in the Makefile (`GOLANGCI_LINT_VERSION`) and fetched on demand via `go run`, so no separate install is needed. A second workflow (`.github/workflows/vuln.yml`) runs `make vuln` (govulncheck) on PRs, pushes to `main`, and weekly. A third runs the release pipeline on a pushed `v*` tag — see **`docs/releasing.md`** for all of it (pipeline, version injection, versioning, prereleases). Beyond the in-tree config, the repo enables (GitHub-side, not visible in the checkout) private vulnerability reporting — security disclosures go through `SECURITY.md` — plus Dependabot security alerts and automated security fixes. Tests use injected fakes and never hit the network (see below), so they're fast and offline.

Run the app: `./lookit` (TUI), `./lookit user@host[:port]` or `./lookit @host[:port]` (opens the TUI seeded with that target), `./lookit -v`/`--version`, `./lookit -h`/`--help`. The TUI requires a real TTY and can't be smoke-tested headlessly. The README hero gif (`demo/demo.gif`) is generated from `demo/demo.tape` with [`vhs`](https://github.com/charmbracelet/vhs) (`vhs demo/demo.tape` from the repo root); the tape fingers `tilde.team`/`graph.no` live and renders with the JetBrainsMono Nerd Font, so re-recording needs network access and that font installed.

**Seeing the TUI: `make review-tui`.** The TUI can't be driven headlessly, but it *can* be looked at — `docs/tui-review/` is a VHS kit that records it as stills (six geometries × two families, plus a contact sheet per tape) for a person or an agent to review. Frames are gitignored, nothing touches the network, and `make check` does not run any of it. Review the PNGs as images; `demo/demo.gif` is marketing, not review material. **Read `docs/tui-review/README.md` before recording or reviewing** — it owns the scene list, the size tiers (`80×24` dark, `80×24` light and `100×30` are first-class; `60×20` is the breakpoint; `100×50` and `45×24` are diagnostic only), the two non-interchangeable rubrics (*is it broken* vs *is it any good*), and the traps already handled in the tapes that must not be undone.

## Architecture

Three packages with a strict one-way dependency direction — `finger/` → `render/` → `tui/` — wired together by `main.go`.

- **`finger/`** — networking only, no UI deps. `ParseTarget` builds the exact wire line (direct forms, one-relay forwarding, `finger://`); `Query` dials, caps, and sanitizes. **`Query` is the single untrusted-input chokepoint:** response bodies are sanitized once at ingress (`sanitize`, sanitize.go), never at a display site, because body-derived bytes reach the terminal by several paths. The symmetric egress guard is `hasControl`, which *rejects* control characters in an outbound query so a hostile target can't smuggle extra RFC 1288 query lines. The bookmarks file is the one other ingress — a user-owned config file, not untrusted network input; it validates rather than sanitizes and displays nothing unvalidated. **See `finger/CLAUDE.md`** for the full contract — read it before changing anything in this package, and note that security-invariant changes are not self-merged (below).
- **`render/`** — pure body rendering, the single path for a finger response body (CLI text and the TUI viewport alike). Metadata never enters this layer, and response bodies are never reflowed at any width — only the error line wraps. It deliberately uses the **v1** `github.com/charmbracelet/lipgloss`; do not migrate it to v2. **See `render/CLAUDE.md`.**
- **`tui/`** — a glow-style state machine on Bubble Tea **v2** (`charm.land/bubbletea/v2`, `charm.land/bubbles/v2`, `charm.land/lipgloss/v2` — note the `charm.land` v2 import paths, not `github.com/charmbracelet`). `Run()` in `run.go` is the only exported entry point, so `main.go` never touches the TUI internals. `appModel` (app.go) owns lifecycle and routes between four sub-models via a `state` enum (`stateReader` | `stateList` | `stateAbout` | `stateStart`). **See `tui/CLAUDE.md`** for the internals that span files: the startpage and its catalog/bookmark assembly, Expanded Help, the request lifecycle, routing, drilling and history.

`main.go`'s `run(args, stdout, stderr) int` is the testable router for the **TUI-only** app: no args → TUI; a single `user@host`/`@host` arg → opens the TUI seeded with that target (replayed through `submit`, the same path a typed target takes); `-v`/`--version`; `-h`/`--help`. `startTUI` is a package var so tests stub it. Exit codes: 0 ok, 1 error.

### Testing approach

Networking and the TUI program are injected, never real: `tui` uses `FetchFunc`/`fetchCmd` (fetch.go) so model tests drive transitions with a stub fetch; `finger` tests spin up a local `net.Listen` server; `main` tests stub `startTUI`. Follow these patterns rather than adding real I/O to tests.

## Conventions

- **Commit messages: Conventional Commits, and do NOT add `Co-Authored-By` or Codex trailers** — this project deliberately omits them (overrides the usual default). The same applies to **PR and issue bodies**: no "Generated with Claude Code" or AI co-author trailers anywhere outward-facing — the contributor owns the work. A `commit-msg` hook (`.githooks/commit-msg`) enforces the `type(optional-scope): description` format; install it once per clone with `make hooks` (sets `core.hooksPath`). It's bypassable with `git commit --no-verify`. **The vocabulary is closed and lives in one place: `scripts/check-conventional-subject.sh`** — standard Conventional Commits types, plus an allowlist of scopes naming real parts of lookit (`tui`, `finger`, `render`, `startpage`, …). A new scope means editing that script, in the same change that first uses it. Two callers share the script so they can't drift: the local hook, and `.github/workflows/commit-style.yml`, which checks the **PR title** — squash merges make the title the subject on `main`, where the hook never runs. So a PR whose title doesn't conform fails CI even if every commit on the branch is clean.
- **Branching: trunk-based, and `main` is protected.** Land every change — maintainer changes included — through a short-lived branch and a PR, never a direct commit to `main`. Branch protection requires the `test` check green and the branch up to date (strict), and blocks force-pushes/deletions, so a direct push of an unchecked commit is rejected. There's no `develop` or standing release branch; a `release/x.y` branch is cut only for a real backport of an old minor. Releases are tags off **green `main`** (never a feature branch); flow: branch → PR → green CI → merge, then tag from `main` (`docs/releasing.md` for versioning and the tag mechanics). Commit/push/PR only when the user asks (see CONTRIBUTING.md for the contributor-facing version). **Edit ≠ ship:** making edits and running the checks is the default unit of work; pushing, opening a PR, or enabling auto-merge each need an explicit go-ahead — don't treat approval to *write* a change as approval to *land* it.
- The local `~/bubbletea`, `~/bubbles`, `~/lipgloss`, `~/glow`, `~/soft-serve`, `~/crush`, `~/wishlist`, `~/pop`, `~/skate`, `~/vhs` clones are reference material only; the versions resolved in `go.mod` are authoritative. After adding a Charm dependency, run `go mod tidy`. (`wishlist`/`pop` are Bubble Tea TUIs — the closest analogues for keymap/help/spinner/list/OSC-52 idioms; `skate` is a cobra+`fang` CLI, a reference for `main.go`'s flag/version handling.)
- **Target platform priority: macOS first.** Optimize the UX for macOS (Terminal.app, iTerm2, Ghostty) — when a default, keybinding, or layout trades off between platforms, pick what's best on macOS. Linux must keep working (no breakage, tests stay green, no platform-specific build breaks), but it's the secondary target: don't compromise the macOS experience to perfect Linux. This is *why* we avoid Alt/Option chords and preserve native macOS copy (see below).
- **UI decisions follow a fixed priority:** first what Charm / `bubbles` binds or does **by default**, then the **vim flavour** those components already use, and only then **smallnet-browser** convention (Gemini/Gopher clients — Amfora, and Bombadillo, which also speaks `finger://`). Check the reference clones for what Charm actually does before choosing, and prefer real `bubbles` components (`help`, `spinner`, `key.Binding` keymaps, `paginator`) and glow's patterns over hand-rolled equivalents. When unsure, the honest answer is often "what does glow do?".
- **Keyboard / macOS gotchas:** avoid `Alt`/`Option` chords — they need the macOS "Option as Meta" setting and collide with `textinput`'s word-motion keys. Don't capture the mouse by default (it breaks native macOS select/copy; glow gates mouse behind an opt-in flag). Pair every colour with a light/dark value (`lipgloss.AdaptiveColor`) rather than hardcoding dark hex, so light terminals stay legible.
- **UI copy is honest:** don't assert structure the finger protocol lacks (e.g. no invented "kind" tag); let derived facts carry meaning (a breadcrumb's *shape* signals directory-vs-profile), and label lookit's own uncertainty plainly and consequence-first (`auto-detected`, `partial (truncated)`).
- **Keep specs focused:** defer cross-cutting concerns (theming, etc.) to their own spec rather than folding everything into one.

### Docs: which ones are living, which are snapshots

- **Living — update them in the same change that makes them wrong.** `docs/user-facing-messages.md` is an inventory of every app-authored string that can reach a user (CLI, renderer, TUI) with its source location and surface; changing, adding or removing user-facing copy means editing that table too. `docs/rfc1288-conformance.md` records lookit's stance on each normative RFC 1288 requirement; changing what goes on the wire means editing that table too. (Both had to be caught up once already — that's why they're called out here.)
- **Snapshots — read for the "why", don't sync.** Design rationale lives in `docs/superpowers/specs/` (specs) and `docs/superpowers/plans/` (implementation plans), phase by phase, plus dated ADR-style records in `docs/decisions/` for standalone calls (e.g. the deliberate choice *not* to send `/W` verbose queries by default) — consult them before changing behavior. **These are point-in-time snapshots, not living specs:** they record the intent at the time of writing. It is fine for the code to deliberately diverge from them later — *provided the deviation is an explicit, recorded decision* (noted in the commit/PR or a follow-up spec), not accidental drift. When code and an older doc disagree, trust the code and the most recent decision.

### Agentic workflow (Claude sessions)

How to land work in this repo when the user asks you to commit/push/PR — the operational version of the branching bullet above.

- **One logical change = one branch = one PR.** Pick the boundary *up front*, before starting, rather than piling mixed work onto one branch and trying to split it afterward (painful and error-prone). If mid-task you find yourself editing an unrelated concern, that's the signal to start a *new* branch, not to keep going. Keep PRs small and self-contained — the threshold for opening one is "a coherent slice is done," not "it's gotten big enough to be worth it." For independent areas in one session, use a branch (and ideally a `git worktree`) per area; for dependent work, **stack** (branch B off A, PR B against A, merge A first).
- **Sync `main` before every new unit — this is step 0, not optional.** The very first action when starting any new branch (a fresh slice, or the next one after a merge) is to run, with no reminder needed: `git fetch origin && git checkout main && git pull --ff-only && git checkout -b <new-branch>`. Do this *before* writing a single line — never branch off a stale `main`. **Why it bites:** merges land on `main` as **squash** commits, so the moment a PR merges your local `main` is behind `origin/main` and your branch's original commits are orphaned; branching off the stale `main` makes the new PR "behind," and strict protection then forces an update-and-re-run. If you just merged a PR in this session, your local `main` *is* stale — sync it. (Branching directly off `origin/main` is the equivalent shortcut.)
- **Ship flow — self-merge on green `test`** (default for code/substantive changes): after the user OKs shipping, run `make check` locally, then `git push -u origin <branch>` → `gh pr create` (no AI trailers in the body) → wait for the `test` check to go green → `gh pr merge --squash --delete-branch`. This repo has **no bot reviewer**, so `test` (the required status check, run by `ci.yml`) is the merge gate; running `make check` first makes a green `test` near-certain. Use `gh pr merge --auto --squash --delete-branch` to have it merge the moment `test` passes rather than polling for it yourself.
- **When NOT to self-merge:** push and open the PR but **leave the merge to the human** when the change touches a security invariant (the `finger/` sanitize ingress/egress, port-79 pinning), is hard to reverse or outward-facing, or you're unsure. When in doubt, surface and wait. (A *pure-docs/Markdown* change is the opposite end — fine to fire-and-forget with `--auto --squash --delete-branch`.)
- **Never direct-push to `main`, even for a one-line docs fix.** `enforce_admins:false` means the *human owner* can bypass protection deliberately for trivial Markdown — that escape hatch is theirs, not yours. The agent default stays the PR path: an agent bypassing protection is a worse failure mode than a human doing it knowingly. Don't worry about CI "cost" for docs PRs — the repo is public, so Actions minutes are free and uncapped.
